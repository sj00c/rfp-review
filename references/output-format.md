# review.json 형식 (make_report.py 입력)

```json
{
  "meta": {
    "사업명": "OO 시스템 고도화 용역",
    "검토일": "2026-10-23",
    "검토자": "구매팀",
    "검토문서": ["입찰공고문(안).hwpx", "제안요청서.hwpx", "원가계산보고서.xlsx"],
    "낙찰방식": "협상",
    "계약유형": "용역",
    "추정가격": 200000000
  },
  "findings": [
    {
      "id": "②-20",
      "항목": "전자입찰 기준 현행화",
      "중요도": "★필수",
      "판정": "수정필요",
      "판정방식": "문서",
      "문서": "제안요청서",
      "위치": "[p.24] Ⅴ.3 제안서 제출",
      "원문": "제안서 인쇄본 10부와 USB 1개를 밀봉하여 제출",
      "요약": "비전자 제출 문구 잔존(인쇄본·USB·밀봉)",
      "문제점": "비전자 제출 문구(인쇄본·USB·밀봉)가 남아 있습니다.",
      "근거": "전자조달법 제11조, 조달청 제안서평가 세부기준 제6조의2",
      "수정안": "제안서 및 가격입찰서는 국가종합전자조달시스템(나라장터)을 통해 전자 제출합니다. (표준문구 S-07)",
      "연계": ""
    }
  ]
}
```

## 판정 값 (4개만 사용)

| 판정 | 쓰는 경우 |
|---|---|
| 수정필요 | 문서에 위반·누락·불일치가 있다. 반드시 `원문`(누락이면 "해당 내용 없음")과 `수정안`을 쓴다. 누락이면 `위치`에 들어갈 자리의 `[문단 n]`을 적어 그 문단에 메모가 달리게 할 수 있다(원문은 비우고 문제점에 "누락" 명시). |
| 확인필요 | 문서만으로 판정할 수 없다([확인] 항목, 외부 목록·결재문서 확인 필요, 판단이 애매함). `문제점`에 **무엇을 어디서 확인할지** 쓴다. 필요하면 `"확인주체": "요청부서"`를 추가한다. |
| 적합 | 문서가 기준을 충족한다. `문제점` 칸에 판단 근거를 한 줄로 쓴다. |
| 해당없음 | 이 건에 적용되지 않는다(예: 적격심사 건의 협상 항목). 시트 전체가 해당없음이면 항목을 나열하지 않아도 된다. |

## 작성 규칙

- `원문`은 문서 문장을 그대로 복사한다. 요약·의역 금지. 길면 중간을 `…`로 줄인다(앞부분~뒷부분이 형광펜 범위가 된다).
  annotate_hwpx.py가 이 문구로 문서에서 위치를 찾는다. 공백 차이는 무시하지만 글자가 하나라도 다르면 못 찾는다.
  문단 전체가 아니라 **문제가 되는 부분만** 인용하면 형광펜이 그 부분에만 칠해진다(예: "인쇄본 10부와 USB 1개를 밀봉하여 제출").
- `위치`는 extract_text 출력의 위치 표시 + 문서 목차 번호/제목. 작성자가 바로 찾을 수 있어야 한다.
- `요약`은 한글 메모의 첫 줄이다. 메모가 접힌 상태에서도 무엇을 고칠지 알 수 있게 **30자 안팎**으로, 문제와 핵심 값을 쓴다. 예: "사업기간 불일치(공고문 6개월 / 제안요청서 5개월)", "폐지된 SW사업자 신고확인서 요구". check_numbers.py는 자동으로 채운다.
- 메모는 `점검ID 중요도 | 요약` → `▶ 수정: 수정안` → `상세: 문제점` → 점검항목·근거 순서로 만들어진다.
- `근거`는 checklist.md의 근거란에 있는 것만 쓴다. 조문을 새로 만들어 내지 않는다.
- `수정안`은 바로 붙여 넣을 수 있는 문장으로 쓴다. standard-phrases.md에 맞는 문구가 있으면 그 문구를 쓰고 번호를 괄호로 적는다.
- 같은 문제가 여러 체크리스트 항목에 걸리면 한 줄로 쓰고 나머지 ID는 `연계`에 적는다.
- **같은 지적이 문서 여러 곳에 나타나면(앞에서 지적한 내용이 뒤에도 공란·중복·같은 위반으로 반복되는 경우 포함) 그 자리마다 메모가 달리게 한다.** finding 하나에는 `원문`이 하나뿐이라 메모도 한 곳에만 달린다. 위치만 한 줄로 나열하면 뒷부분을 보는 작성자는 "여긴 왜 지적이 없지?" 하고 놓친다. 그래서 지적을 올리는 **본 항목**(`원문`=첫 위치) 외에, **추가 위치마다 참조용 finding을 따로 올린다**:
  - `id`는 본 항목과 같게(예: 본 항목 `②-5` → 참조도 `②-5`), `중요도`는 `참고`, **`"참조": true`** 를 넣는다. 단 `항목`은 본 항목과 **다르게** 쓴다(예: `"과업명·목적·대상·업무범위 기재(②-5 참조)"`). annotate_hwpx.py는 `(id, 항목)`으로 finding을 식별하므로, id·항목이 모두 같으면 본 항목이 참조 메모로 덮어써져 사라진다.
  - `요약`은 `"②-5 참조 — <무엇을 고칠지>"`처럼 **어느 메모의 내용인지 먼저 밝힌다**(작성자가 본 지적을 바로 찾아갈 수 있게).
  - `원문`에는 그 위치의 문구를 넣어 거기에 메모가 달리게 한다. 공란이면 그 자리의 라벨 문구를 넣는다(예: `1. 과업명`). `위치`의 `[문단 n]`을 그 문구가 실제로 있는 본문 문단으로 적는다(목차에 같은 문구가 있으면 본문 문단 번호를 hint로 줘야 목차가 아닌 본문에 달린다).
  - `연계`에 본 항목 ID를 적고, `판정`은 본 항목과 같게 둔다(형광펜 색이 같아진다).
  - `"참조": true`가 있으면 annotate_hwpx.py가 메모는 그려도 **'수정 요청 n건' 건수에는 세지 않는다**(같은 문제를 가리키는 포인터이므로).
- check_numbers.py가 낸 항목을 다시 판단할 때는 같은 `id`·`항목`으로 review.json에 쓰면 덮어쓴다(이유를 `문제점`에 적는다).
